# Security

## Trust boundaries

| Caller | Authentication | What it can reach |
|---|---|---|
| Shopper (storefront) | SFRA session, registered and signed in; HTTPS; CSRF on every POST | Own wallet; family wallet only as an active member, within limits |
| Shopper (headless) | SLAS registered-shopper token, scope `c_wallet` | Own wallet through `/me` paths |
| Payment gateway | HMAC-SHA256 signature with timestamp (`plugin-wallet.webhook`), event replay guard | Top-up status of its own references |
| OMS / back office | Account Manager client, scope `c_wallet_admin` | Refunds, chargebacks, wallet status, holds |
| Customer service | Business Manager login with the Smart Wallet module permissions | Wallets, cases, audit |

## Money integrity

- **Server-side amounts only.** No route or API takes a wallet amount at face value: the applied amount is recomputed from the basket total, the balance and the limits; the hold amount is the payment instrument amount calculated by the server.
- **Balanced, append-only ledger.** Every movement is a journal whose postings balance; entries and journals are never edited or deleted. Corrections are new reasoned journals (adjustment reason ≥ 10 characters, capped by `walletAdjustmentMaxCents`).
- **No double spend.** The sequenced entry key collides for concurrent writers and the platform rolls one transaction back. Negative balances are refused.
- **Idempotency.** Journals are keyed by business keys (`TOPUP:<id>`, `HOLD:<id>`, `REFUND:<refundId>`), webhook events by event ID. Repeating a request returns the first result; reusing a key with other data is a `CONFLICT`.
- **Verified top-ups only.** Credits happen only after `verifyPayment` confirms CAPTURED with the same amount, USD and reference. A browser return or a webhook body never credits. Mismatches open a `GATEWAY_MISMATCH` case.
- **Status flows.** Every status change is checked against the status-flow table of its helper (`walletHelpers.canMove`), so replays, second job runs or stale pages cannot move a record backwards. A captured hold can never be released.
- **Reconciliation.** `Wallet-Reconcile` replays every wallet against its snapshot, checks journal balance and compares captured holds with order payment instruments.

## Authorization

- The payer must be the signed-in customer: the owner, or an `ACTIVE` member of that wallet. Authorize re-checks this at order placement, so a revoked or paused member cannot pay even with a prepared basket.
- Members see only their remaining allowance, never the owner's balance or history (tested).
- A locked wallet cannot pay. Only owner-set locks can be lifted by the owner (with a code). Locks from failed codes or chargebacks, and freezes, need customer service; only customer service can unfreeze.
- Business Manager: four modules (Overview, Wallets, Cases, Audit trail) are separate menu actions, each with its own permission. No node uses `NoPermissionCheck`.

## Step-up verification

- A one-time code is required for payments at or above `walletStepUpThresholdCents` and from sessions that have not paid with the wallet before (`walletRecentSessionsTracked`, stored as hashes).
- A code or approval is bound to the payer, the basket and the exact amount, expires (`walletOtpTtlMinutes`, `walletApprovalTtlMinutes`) and is consumed by the authorization.
- Codes are generated by `SecureRandom`; only a keyed hash of salt + code is stored. Codes are bound to the session that requested them, rate-limited (`walletOtpMaxSendsPerHour`, `walletOtpResendCooldownSeconds`) and locked after `walletOtpMaxAttempts`. Repeated locked codes lock the wallet and open a `FAILED_CODES` case.

## Family invitations

Invitation tokens are 48 hex characters from `SecureRandom`; only their keyed hash and a keyed hash of the e-mail address are stored. Acceptance needs the signed-in account's e-mail to match and a code sent to that address. A customer can belong to one family wallet and cannot invite themselves.

## Data protection

- No card data is handled; card payments stay with the existing card processor.
- Custom objects store no codes, tokens or e-mail addresses in clear text. Notifications store the customer number; the address is looked up at send time.
- Logs never contain codes, tokens, secrets or e-mail addresses. Errors to the shopper or API caller carry only the code and safe detail.
- Secrets are Service Framework credentials (`plugin-wallet.hmac`, `plugin-wallet.webhook`), not code or preferences.

## Fraud and abuse controls

| Control | Where |
|---|---|
| Top-up range, maximum balance (with pending), daily count and amount | `walletTopUpHelpers.startTopUp`; `TOPUP_VELOCITY` case |
| Spending limits per transaction, day and month; member limits and categories | `walletAccountHelpers.checkSpendLimits`, `walletFamilyHelpers.checkMemberLimits` |
| Refund cap (captured − refunded) and refund abuse cases | `walletPaymentHelpers.refundToWallet`, `Wallet-Risk` |
| Chargeback reversal, shortfall tracking and lock | `walletTopUpHelpers.reverseTopUp` |
| Rate limits on top-ups and invitations | `walletHelpers.checkRateLimit` (`walletWriteRateLimitPerHour`) |

## Sandbox safeguards

- SANDBOX mode is the default and every sandbox page and badge says "Not for Live Money".
- `walletHelpers.canTopUp()` refuses sandbox top-ups on a production instance (`System.PRODUCTION_SYSTEM`).
- EXTERNAL mode needs `walletLiveMoneyApproved = true`; without it Business Manager shows a preference problem and top-ups are refused.

## Production blockers

All open. None of them can be closed by code alone.

1. **Regulatory classification and approval.** Stored value may be regulated as prepaid access (FinCEN, 31 CFR 1010.100(ww)), as money transmission under state laws, and under gift-card rules (CARD Act / Regulation E 12 CFR 1005.20 and state escheatment). Legal must decide whether the program is closed-loop, which state rules apply, and approve the terms of use, privacy notice and dispute handling. Only then set `walletLiveMoneyApproved`.
2. **Licensed gateway.** Implement `app.plugin.wallet.gateway` for a PCI DSS compliant provider with server-to-server verification and signed webhooks. Run the provider's certification.
3. **Funds safeguarding and accounting.** Decide how balances are held and booked (liability / deferred revenue), and reconcile `Wallet-Reconcile`, the provider settlement and the general ledger daily.
4. **Refunds of balances, dormancy and escheatment.** Define cash-out on request, closing a wallet with a balance, and unclaimed-property reporting. Keep `walletFundsExpiryDays = 0` until approved.
5. **Shipping benefit terms.** If used, the promotion and its customer-group rule need marketing and legal approval.
6. **Security review and penetration test** of the wallet routes, Custom APIs and webhook on a sandbox.
7. **Sandbox verification** spikes W1–W10 in [TESTING.md](TESTING.md#sandbox-verification-plan).
